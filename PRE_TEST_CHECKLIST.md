# Чек-лист перед пилотным тестированием

Релиз `stud_hunter_forms_base` — это тестовая ветка без AI-респондентов и без
импорта из Google/Яндекс Форм. Ниже — то, что нужно закрыть **до** того, как
позвать настоящих респондентов.

---

## 1. Безопасность (обязательно)

- [ ] **`JWT_SECRET`** — заменить дефолт `change-me-in-prod-please` в
      `docker-compose.yml` на длинную случайную строку (минимум 32 байта,
      `openssl rand -hex 32`). Если уже выкатили со старым секретом — после
      замены все пользователи разлогинятся, это нормально.
- [ ] **`CORS_ORIGINS`** — заменить `*` на конкретный домен фронта,
      `https://forms.example.com` (через запятую можно несколько). Звёздочка
      + `allow_credentials=True` в проде небезопасно.
- [ ] **HTTPS** — поднять nginx/Caddy/Cloudflare перед бэком и фронтом,
      без `https` cookie/токены текут открытым текстом.
- [ ] **Пароль БД** — `POSTGRES_PASSWORD: hse` в `docker-compose.yml` поменять
      на нечто непредсказуемое.
- [ ] **Rate-limit** — проверить, что `slowapi` действительно навешен на
      `/auth/register`, `/auth/login` и публичный submit, иначе перебор по
      паролям и спам ответами ничем не ограничен.
- [ ] **Открытые порты** — закрыть наружу `5432` (Postgres) и `6379` (Redis),
      сейчас они проброшены для удобства разработки.

## 2. Бэкенд — проверка работоспособности

- [ ] `docker compose up --build` поднимается с чистого диска, alembic
      `upgrade head` отрабатывает без ошибок.
- [ ] `GET /health` отвечает `{"status":"ok"}`.
- [ ] В БД остались колонки `responses.is_synthetic` и
      `responses.synthetic_profile` от прошлой версии — они безвредны,
      дефолты `false` / `{}`. **Не дропать миграцией без бэкапа.**
- [ ] Проверить, что эндпоинтов `/surveys/{id}/synthetic/run` и
      `/surveys/{id}/import` **нет**: `curl -i …` должен дать 404.

## 3. Фронтенд — production-сборка

- [ ] `flutter build web --release --dart-define=API_BASE=https://api.example.com`
      (если бэк и фронт на разных хостах). Без `--dart-define` фронт по
      умолчанию шлёт запросы на `${origin}:8000` — это работает только если
      бэк действительно на 8000-м.
- [ ] `frontend/nginx.conf` должен отдавать `index.html` на все маршруты
      (`try_files $uri /index.html;`), иначе при F5 на `/builder/42`
      пользователь получит 404 от nginx.
- [ ] Проверить заголовок страницы, favicon, web manifest (`frontend/web/`).
- [ ] Прогнать `flutter analyze` — должно быть 0 errors / 0 warnings
      (текущие 54 issues — info-level стилевые, на работу не влияют).

## 4. Функциональная проверка (пройти руками)

Создать тестовый опрос и пройти весь цикл:

- [ ] Зарегистрироваться → войти → выйти → войти снова (токен сохраняется).
- [ ] Создать опрос, добавить **каждый** тип вопроса:
      короткий/длинный текст, один/несколько/выпадающий выбор, шкала, секция.
- [ ] Включить «обязательный» — убедиться, что без ответа респондент
      не может отправить.
- [ ] Добавить разделитель страниц (`page_break_before`) и условный показ
      (`displayCondition`) — пройти и убедиться, что ветвление работает.
- [ ] Опубликовать, открыть публичную ссылку **в режиме инкогнито**
      (важно — без токена), пройти опрос.
- [ ] Отправить 5–10 ответов с разных устройств, открыть «Аналитику» —
      графики строятся, ничего не падает.
- [ ] Анонимный режим: убедиться, что в `responses` поле `user_id` пустое.
- [ ] «Один ответ от пользователя»: вторая попытка от того же
      пользователя/устройства должна блокироваться.
- [ ] Кнопка «Назад» в опросе работает при включённом `allow_back_navigation`.
- [ ] Соавторы: пригласить второго аккаунта, проверить роли (viewer/editor).
- [ ] **Мобильная вёрстка**: верхний бар не должен наезжать
      (мы это починили — повторно проверить на реальном телефоне, не только в
      эмуляторе DevTools).

## 5. Эксплуатация

- [ ] **Бэкап БД** — настроить `pg_dump` хотя бы раз в сутки,
      хранить минимум 7 дней. До пилота сделать снапшот.
- [ ] **Мониторинг** — UptimeRobot/Healthchecks.io на `/health` каждую
      минуту. Алерт в Telegram/почту.
- [ ] **Логи** — куда пишутся, как ротируются. Docker по умолчанию пишет
      в `/var/lib/docker/containers/*` без ограничения размера, забьёт диск.
- [ ] **План отката** — записать чёткие шаги: `git checkout <tag>`,
      `docker compose down && up --build`, восстановление БД из дампа.
- [ ] **Доступ для админа** — у кого продовые ssh/JWT, как ротировать,
      что делать, если человек уходит.

## 6. Юридическое / этическое (для опросов на людях)

- [ ] Согласие на обработку данных — короткий текст на стартовой странице
      опроса. Особенно если собираете ФИО, email, или любые персональные
      данные. Сейчас этого экрана нет — нужно добавить либо в
      `RunnerScreen` (вступительный экран), либо в описание опроса.
- [ ] Решить, что хранится в `synthetic_profile` / `meta` и можно ли это
      связать с конкретным человеком.
- [ ] Если опрос идёт через ВШЭ — согласовать с этическим комитетом и
      указать контакт ответственного.

## 7. Логистика пилота

- [ ] Узкая группа сначала — 10–30 человек, желательно знакомых, чтобы
      ловить баги быстро.
- [ ] Канал обратной связи (TG-чат, форма для багов) — заранее запостить.
- [ ] Запланировать «дежурного по релизу» на первые 2–3 дня после запуска.
- [ ] Подготовить FAQ для респондентов: что делать, если не отправляется,
      куда писать, какие браузеры поддерживаются.

| Фича | Почему | Где осталось |
|---|---|---|
| AI-респонденты (`synthetic`) | Нестабильный вывод LLM, ошибки парсинга JSON, зависимость от внешнего API | основная ветка `stud_hunter_forms` |
| Импорт из Google/Яндекс Форм | Только что добавлено, не протестировано на разнообразии форм | основная ветка `stud_hunter_forms` |
| LLM-зависимости (`httpx`, ключи Groq/OpenRouter) | не нужны без AI | — |

После пилота вернуть фичи обратно — простой `git merge` из основной ветки.
